# Benchmarks

Repeatable k6 scenarios. Everything runs inside Docker on the Compose network,
so the direct and gateway paths cross the same virtual network.

| Script | What it measures |
|---|---|
| `k6/direct.js` | Baseline: k6 → backend-a directly |
| `k6/gateway.js` `MODE=uncached` | k6 → Relay `/api/bench` → backend-a (no cache; same single upstream as direct) |
| `k6/gateway.js` `MODE=cached` | k6 → Relay `/api/bench-cached` with 50 repeating keys (cache-friendly) |
| `k6/failure.js` | Steady load on `/api/bench-ha` (backend-a + backend-b); backend-b fails between t=20 s and t=50 s; reports client errors plus gateway retry/breaker counters |
| `k6/ratelimit.js` | One client alternating between two gateways on `/api/orders`; checks the total allowed stays within capacity + rate × duration |

## Run

```bash
scripts/run_benchmarks.sh                       # full suite, 3 runs each (~35 min)
QUICK=1 RUNS=1 PROFILES=baseline scripts/run_benchmarks.sh   # 2-minute pipeline check (results go to results/tmp/, git-ignored)
```

Each run directory in `results/<timestamp>/` contains:

* `<scenario>-run<N>.json`: raw k6 summary export
* `<scenario>-run<N>.txt`: k6 stdout, including gateway counters for the failure scenario
* `<scenario>-run<N>.stats.csv`: `docker stats` samples (about 1/s) during the run
* `environment.txt`: machine, OS, Docker, versions, topology
* `SUMMARY.md`: generated by `scripts/summarize_benchmarks.py` from the files above

Single ad-hoc runs:

```bash
docker compose --profile bench run --rm -e VUS=10 -e DURATION=30s k6 run /scripts/direct.js
docker compose --profile multi up -d   # needed for ratelimit.js
```

## Fairness rules used

* Same machine, same Docker VM, same mock backend, same request mix.
* The direct baseline and the uncached gateway route both hit backend-a only.
* Scenarios are interleaved within each run, so drift affects all equally.
* No other heavy work on the machine while the suite runs.
* Results are reported as median and range; nothing is discarded.
